# Oficina

Oficina is a personal fork of [Orca](https://github.com/stablyai/orca) (MIT). It exists to put whole workspaces side by side in one window. Everything else stays stock Orca so merges from upstream stay cheap.

This page covers step 0: Oficina builds and runs as its own app, next to the installed Orca, without touching anything Orca owns.

## What Oficina changes vs Orca

- **Own identity.** One module, `src/shared/oficina-identity.ts`, owns every machine-global name (table below). `config/oficina-identity.cjs` mirrors it for electron-builder; `src/main/startup/oficina-identity.test.ts` fails if they drift.
- **Agent status: receive, never install.** Orca's installers write `~/.orca/agent-hooks` and the Claude, Codex, Cursor, Gemini... user configs. Those belong to the official Orca, so the fork never writes or removes them (`isAgentStatusHooksEnabled` is false, installers and removers are no-ops). The fork does run the local hook receiver and exports its address into its own terminals (`agentStatusReceiverEnabled`), so the scripts the official Orca already installed report to Oficina when an agent runs in an Oficina terminal. The receiver follows the saved Agent status switch (Settings > Agents), so a profile that saves it off hears nothing and cannot resume agent sessions. See "Agent status without installing hooks" and "Resuming agent conversations".
- **No auto-update.** The updater never loads, no `app-update.yml` is packaged, and the agent-state-rules download from stablyai release assets is off.
- **Own global CLI command.** Settings can register `oficina`, never `orca` (Orca's installer would otherwise reclaim any `*.app` launcher symlink, including Orca's).
- **No computer-use helper and no file associations** in the bundle (shared bundle id with Orca; extra Open-With rows).
- **Packaging lives beside upstream.** `config/electron-builder.oficina.config.cjs` wraps the untouched upstream builder config; `config/scripts/oficina-local.mjs` builds, signs, installs and seeds data.
- **Branding.** The page and window title, the app name at the top of the sidebar, and the Help and tray labels say Oficina, through `src/shared/oficina-product-name.ts` (`withProductName`). Locale catalogs are untouched; "Orca Mobile" keeps its name because the phone app is still Orca's.
- **Tests.** `config/scripts/vitest-upstream-identity-setup.ts` runs the inherited suites against upstream names (`.orca`, 6768, hooks on) so they stay unedited. `oficina-*` tests pin the fork's real values.

## Build and install locally

Run everything through Node 24 (`fnm exec --using 24 -- ...`, `COREPACK_ENABLE_DOWNLOAD_PROMPT=0`). The machine default Node 26 is not supported.

```sh
fnm exec --using 24 -- pnpm install --frozen-lockfile                 # root
(cd mobile && fnm exec --using 24 -- pnpm install --frozen-lockfile)  # mobile web bundle needs its own install
fnm exec --using 24 -- node config/scripts/oficina-local.mjs build    # JS build, helpers, arm64 .app, signing
fnm exec --using 24 -- node config/scripts/oficina-local.mjs install  # copies to /Applications/Oficina.app (--replace removes the old bundle first; refuses while Oficina runs)
fnm exec --using 24 -- node config/scripts/oficina-local.mjs import-orca-data
```

A clean build took 110 s on a 10-core M-series Mac (typecheck+JS 38 s, helpers 10 s, electron-builder 30 s, signing 33 s), plus 6 s for the root install and 24 s for the mobile install.

`build` runs `build:desktop`, which ends in `install-dev-cli.mjs`; it tries to link `/usr/local/bin/orca-dev` and is refused without sudo. That is harmless and leaves `orca` alone.

### Signing identity (once)

The bundle is signed with a self-signed identity so macOS sees the same designated requirement on every rebuild and keeps folder-access grants. No hardened runtime, no notarization.

```sh
cat > openssl.cnf <<'EOF'
[req]
distinguished_name=dn
x509_extensions=v3
prompt=no
[dn]
CN=Oficina Local Signing
[v3]
basicConstraints=critical,CA:false
keyUsage=critical,digitalSignature
extendedKeyUsage=critical,codeSigning
EOF
openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 3650 -config openssl.cnf
PW=$(openssl rand -hex 12)
openssl pkcs12 -export -inkey key.pem -in cert.pem -out id.p12 -name "Oficina Local Signing" \
  -passout pass:$PW -certpbe PBE-SHA1-3DES -keypbe PBE-SHA1-3DES -macalg sha1
security import id.p12 -k ~/Library/Keychains/login.keychain-db -P "$PW" -T /usr/bin/codesign
# then delete key.pem and id.p12; the key stays in the keychain
```

`security find-identity -p codesigning` lists it as `CSSMERR_TP_NOT_TRUSTED`; that is expected for a self-signed certificate and does not stop `codesign`. The designated requirement is `identifier "com.vitorf91.oficina" and certificate leaf = H"<sha1 of the certificate>"`.

### Data import

`import-orca-data` reads the official Orca's `profiles/local-default/orca-data.json` (read-only) and writes a filtered `orca-data.json` into Oficina's data folder. Oficina imports it into its own SQLite profile on first launch.

- Kept: repos, projects, project groups and host setups, folder workspaces, settings (the Agent status switch stays as Orca had it: the fork's receiver follows it, and the installers are off by identity, not by this value), a few sidebar view preferences.
- Dropped: sessions, terminals, PTY ids, worktree metadata, SSH targets, account/auth settings, API keys and cookies, proxy URL, mobile pairing, telemetry consent, `agentDefaultEnv`.
- A copy is refused if any kept key name or value looks like a secret, or points into Orca's folders. Orca's device tokens, E2EE keys and account session files are never copied.
- It refuses to run over an existing Oficina profile.

## Coexistence check

Run this after any sync from upstream:

1. Snapshot (hash, size, mtime) the files Orca owns: the `~/.orca` tree, the user agent configs (`~/.claude/settings.json`, `~/.codex/{config.toml,hooks.json}`, `~/.cursor/hooks.json`...), the `/usr/local/bin/orca` symlink, `Orca.app`'s plist/executable/seal, Orca's preferences plist and runtime pointer files; plus the LaunchServices handler for `orca://` and `oficina://`, the `orca Safe Storage` keychain attributes and any Orca or Oficina launch agents.
2. Launch Oficina, open a terminal in a worktree, quit it (its own PIDs only).
3. Snapshot again and diff. Expected: identical, `orca://` still `com.stablyai.orca`, only `Oficina Safe Storage` new.

The first run of this check wrapped Oficina in `sandbox-exec` with a profile that denies writes to those paths. Chromium cannot nest its own sandbox inside that one, so the wrapped run used `--no-sandbox`; a normal launch does not.

## Agent status without installing hooks

The hook scripts the official Orca installs hold no address of their own. Claude's `settings.json` runs `/bin/sh "$HOME/.orca/agent-hooks/claude-hook.sh"` (`claude/hook-settings.ts:85`); that script sources `$ORCA_AGENT_HOOK_ENDPOINT` when it is set (`claude/hook-script.ts:85-87`), needs `ORCA_AGENT_HOOK_PORT`, `ORCA_AGENT_HOOK_TOKEN` and `ORCA_PANE_KEY` (`:89`), and posts to `http://127.0.0.1:$ORCA_AGENT_HOOK_PORT/hook/claude` with the token header (`agent-hooks/hook-post-command.ts:14-18`). The receiver accepts only that token (`agent-hooks/server/server-lifecycle.ts:55`). Every address therefore comes from the environment of the terminal the agent runs in. Orca's terminals carry Orca's address and report to Orca; an Oficina terminal carries Oficina's.

What the fork does:

- **Receiver on.** `agentStatusReceiverEnabled` starts the listener (`main-process-pty-startup.ts:180`) and keeps it in step with the Settings switch (`main-process-ready-foundation.ts:254`). It writes only `<Oficina data>/agent-hooks/` (the endpoint file, `last-status.json`, the spool folder).
- **Address exported.** `host-env/assembly.ts:153` adds `agentHookServer.buildPtyEnv()` to every terminal even though installers are off. The loop above it (`:116`) first deletes any `ORCA_AGENT_HOOK_*` inherited from the process, so an Oficina started from an Orca terminal never passes Orca's address on. If the user switches status off, `buildPtyEnv` returns nothing and the terminal carries no address at all.
- **Installers still off.** `isAgentStatusHooksEnabled` stays false, so no install, refresh or removal runs, and the other PTY-time work that sits behind that switch (Pi, OMP, OpenCode and Mimo status plugins, Codex hook reconcile) stays off too. The headless server (`orcad`) still reads the installer switch (`orcad-entry.ts:202`, `:266`), so it keeps the receiver off.

Covered and verified: Claude. In the e2e harness (`oficina-agent-status-receiver.spec.ts`, disposable HOME) the official script and wrapper are laid out in `$HOME/.orca/agent-hooks`, then run from an Oficina terminal with an inherited fake Orca address in the app's own environment: the terminal names Oficina's endpoint and port, prompt, permission request and stop events show Working, Needs attention and Done in the UI, and the fake Orca receiver hears nothing (it records a control request first, so silence is meaningful). The installed Orca 1.4.212 hooks were also exercised for real, from the installed `/Applications/Oficina.app` with a throwaway profile (`--user-data-dir`), a hidden window driven over CDP, and the real `~/.claude/settings.json` and `~/.orca/agent-hooks/claude-hook.sh` untouched: `claude -p "reply with the word pong"` typed into an Oficina terminal in a scratch repo under `/tmp` printed `pong`, exit 0, twice. Oficina's own store (`agentStatus.getSnapshot`) held one `claude` row with origin `hook`, authority `main-agent-hooks`, and state `done`; the sidebar card and the terminal tab showed the Working spinner while the turn ran (the hook's turn-start and stop times matched the UI changes to within 10 ms), then Done. The terminal named Oficina's own endpoint file and listener port, both under the throwaway profile. Afterwards a before/after snapshot of 60 Orca-owned entries (`~/.orca` tree, `~/.claude/settings.json`, `~/.codex`, `~/.cursor`, `~/.gemini`, `~/.copilot`, `/usr/local/bin/orca`, `Orca.app`'s plist, executable and seal, Orca's preferences and runtime pointer files, LaunchAgents) was identical, Orca's own persisted status rows held none of the run's pane or tab ids, and the real Oficina data folder was unchanged.

Not covered: agents whose status comes from a plugin or extension that the official Orca installs per agent (for example OpenCode and Pi). Those load from agent config folders that the fork does not write, so they keep the title-based status. Codex, Cursor and the other script-based agents use the same environment contract, but only Claude was run end to end; a Codex started under a managed Codex home was not exercised.

## Resuming agent conversations

Opening a worktree that had an agent session brings the conversation back the way the official Orca does it. The agent reports its provider session id through the hook scripts the official Orca installed; the receiver turns that into a resume record for the pane; and the record survives Sleep, a quit that lost the daemon and a hibernation. Opening the worktree again types `claude --resume <id>` (or the agent's own resume command) into a new terminal of that worktree.

What the fork needs for this: the receiver on (Settings > Agents > Agent status), and the official Orca's hook scripts in place. No file is written by the fork. Terminals started before the switch is turned on keep their old environment, so open a new terminal after turning it on.

Why a profile imported before the fix did not resume: `import-orca-data` used to save the switch off ("the fork keeps hooks off"), and the receiver follows that switch. The terminals then carried no hook address, claude's reports went nowhere, and no resume record was ever written, while the title-based status looked normal. Installers were never the problem: with the switch on, every other consumer below already behaves, which `tests/e2e/oficina-agent-session-resume.spec.ts` shows end to end (typed `claude`, then Sleep and reopen, quit with the daemon killed, a terminal the runtime creates, and a profile made by the real importer), with a disposable HOME that keeps the files an official Orca leaves behind and fails if any of them changes.

Auto-hibernation is separate: it is the experimental "Agent hibernation" setting and is off by default. Manual Sleep and a restart resume without it.

### A Claude session started in the official Orca

Its terminal lives in the official Orca's own daemon, so the fork cannot attach to it or show its live status. What the fork can do: Agent Session History scans `~/.claude/projects` (read-only), lists the session under its project, and "Resume in Worktree" opens an Oficina terminal running `claude --resume <id>` (covered by the same spec, with a transcript seeded under the disposable HOME). Resume only after the session ended in the official Orca: while it still runs there, a second `claude` on the same session would write to the same transcript (not exercised; the fork has no view of that process).

### Consumers of the hooks switch

`isAgentStatusHooksEnabled` and `isAgentStatusHooksEnabledForAgent` are the fork's "installers on" answer and are always false (`agent-status-hooks-setting.ts`). A consumer is class a when it installs, refreshes or removes user-wide hook files, configs or plugins (it must stay on that switch, so it stays off), and class b when it reads events, session ids or status, or exports an address (it should follow `isAgentStatusReceiverEnabled`). `src/main/agent-hooks/oficina-hook-flag-consumers.test.ts` fails when a merge adds a consumer that is not in this table, and `oficina-hook-installers-off.test.ts` checks the entry points under the real identity.

## Impact and limits

- **Resume needs the same.** A conversation is resumable only if the hook scripts reported its session id to the fork, so it is limited to what "Agent status without installing hooks" covers: Claude is proven end to end; Codex and the other script-based agents share the contract but were not run; agents that report through a plugin (OpenCode, Pi) cannot be resumed from the fork.
- **Agent status needs the official Orca's hooks.** Oficina reports state only for agents whose hook scripts the official Orca installed and keeps in place. If Orca's hooks are removed (its own Settings switch), Oficina's sidebar falls back to the title-based status. Hook scripts fire for every Claude session, so a Claude running in an Orca terminal and one in an Oficina terminal each report to their own app.
- **Branding.** Renamed: page and window titles (index, pop-out dashboard and web entries, at build time), the app name at the top of the sidebar, the Help menu's "Explore" and "Getting Started" items, the tray menu and tooltip. The app menu, About, Hide and Quit use the app name Electron reports, which is Oficina. Not renamed: "Orca Mobile" and pairing copy about the phone app, the roughly 800 locale catalog lines that mention Orca, crash and recovery dialogs, the CLI-unavailable dialog, in-app tips ("Enjoying Orca?") and the empty-state "ORCA" wordmark, and the Windows-only tray notice.
- **Computer-use is absent** from this build, and nothing in the fork can reach Orca's helper or its permissions.
- **First launch from Finder or the Dock** asks macOS for Documents access once (the repos live there). Click Allow; the stable signature keeps the grant across rebuilds.
- **A keychain prompt after each rebuild.** Electron reads "Oficina Safe Storage" from the login keychain at startup. Most likely because a freshly built, self-signed binary counts as a new application to the keychain, macOS can hold the app on an access prompt until someone answers it with the login password. The first real launch after the last rebuild blocked the main thread inside `SecItemCopyMatching` for over a minute (process sample, no window); launching with `--use-mock-keychain` avoided it. Allow it once; choose Always Allow so the grant stays for that build.
- **A leftover "closed unexpectedly" dialog** from an automated test crash may show on first launch. Choose Don't Send.
- **Do not click "Install CLI & Skills"** in the feature tip. It installs the CLI link and agent skills into user-wide folders (see the audit row above), and it runs only on that click.
- **Self-signed, not notarized.** Gatekeeper would reject a downloaded copy; a locally built one runs.

## Keeping upstream merges cheap

Upstream files changed for the identity are one-line swaps to `OFICINA_IDENTITY` (measure against the last merged release: `git diff "$(git tag --merged oficina --sort=-v:refname 'v[0-9]*' | grep -E '^v[0-9]+\.[0-9]+\.[0-9]+$' | head -1)" oficina --stat`). `config/electron-builder.config.cjs` is untouched. After a sync (next section), check the coexistence checklist: `orca://` still resolves to Orca, `/usr/local/bin/orca` still points into Orca.app, and `~/.orca` and the user agent configs are unchanged after a launch.

## Syncing with Orca

`pnpm oficina:sync` (`config/scripts/oficina-sync.mjs`) brings the newest stable Orca release into `oficina`. Run it through Node 24, from a clean checkout; a throwaway worktree keeps the main clone untouched.

```sh
git worktree add --detach ~/Documents/oficina-wt/sync-run oficina && cd ~/Documents/oficina-wt/sync-run
COREPACK_ENABLE_DOWNLOAD_PROMPT=0 fnm exec --using 24 -- pnpm oficina:sync                 # merge, install, gates; leaves a local sync/<tag> branch
COREPACK_ENABLE_DOWNLOAD_PROMPT=0 fnm exec --using 24 -- pnpm oficina:sync --push --merge  # also open the PR into oficina, then merge it with a merge commit and delete the branch
COREPACK_ENABLE_DOWNLOAD_PROMPT=0 fnm exec --using 24 -- pnpm oficina:sync --install       # also install over /Applications/Oficina.app (refuses up front while Oficina runs)
COREPACK_ENABLE_DOWNLOAD_PROMPT=0 fnm exec --using 24 -- pnpm oficina:sync --gates-only    # no merge: install and run the gates on this checkout
```

Flags combine; `--merge` needs `--push`. `--commit-trailer=<line>` adds a line to the merge commit message and `--notes-file=<path>` appends a file to the PR body (conflict notes). After `--merge`, fast-forward the main clone: `git fetch origin && git merge --ff-only origin/oficina`.

What it does, in order:

1. Refuses a dirty tree, a Node other than 24, and a local `oficina` that differs from `origin/oficina`.
2. Lists the published upstream releases and takes the newest stable one (`vX.Y.Z`, not a draft or prerelease) that is newer than the newest stable tag already merged into `oficina`, then fetches that one tag. If there is none it says so and exits 0.
3. Merges that tag into a new `sync/<tag>` branch with a merge commit (`--no-ff`).
4. Installs dependencies with the frozen lockfile (root and `mobile/`), then runs the gates below in order and stops at the first failure. Nothing is pushed or installed unless every gate passed.
5. Prints a summary with the tag, each gate and its duration; the PR body carries the same table.

| Gate              | What it covers                                                                                                                                                                                                                                                                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm tc`         | Node, CLI and web TypeScript projects compile against the merged upstream.                                                                                                                                                                                                                                                                              |
| Unit tests        | Every tracked test file Oficina changed against the last merged release, plus every tracked test whose file name contains `oficina`, `workspace-split` or `workspace-pane`: the identity module and its CJS mirror, the builder wrapper, the sync selection logic, the split layout, storage, drop and pane code. Listed in the output before they run. |
| E2E specs         | Every spec Oficina changed against the last merged release, plus the `workspace-split-*`, `workspace-pane-header` and `oficina-agent-status-receiver` specs through the repo's Playwright harness, whose global setup builds with `electron-vite build --mode e2e`. They use disposable user data and HOME, never the real Oficina profile.             |
| Changed-code lint | `check-changed-code-quality.mjs` against the release tag: every line Oficina changed on top of upstream, under the new release's lint rules.                                                                                                                                                                                                            |
| Packaged build    | `oficina-local.mjs build`: JS build, native helpers, electron-builder, local signing. It refuses a dirty tree, stamps the build id from `HEAD`, and fails if `app.asar` holds test output or the stamp is not `HEAD`.                                                                                                                                   |

The gates cannot tell whether the app feels right. After an install, launch Oficina once and run the coexistence checklist above.

### When the merge conflicts

The script aborts the merge (no half-merged state, no leftover branch), lists the conflicting files and prints how to reproduce. Then:

1. `git switch -c sync/<tag> oficina && git merge --no-ff <tag>`, resolve keeping both upstream's change and Oficina's behaviour (`src/shared/oficina-identity.ts`, the workspace-split files and the `config/*oficina*` files are Oficina's), and `git commit`.
2. Write the file, the cause and the resolution of each conflict into a notes file, and run `pnpm oficina:sync --push --merge --notes-file=<path>` again. On a `sync/<tag>` branch that already contains the tag, it skips the merge and runs the gates.

Prefer resolutions that shrink Oficina's footprint in upstream files, so the next merge is cheaper.

Things the first real sync (v1.4.224, 268 commits) taught:

- Run `pnpm install --frozen-lockfile` before the hand `git commit`: it runs the pre-commit hook (`lint-staged`) over the whole upstream diff. That hook enforces the repo's lint rules on files Oficina touched (an upstream file sitting at the 300-line `max-lines` limit failed on Oficina's one extra import line; shorten the code, never add a disable) and `oxfmt --write` can reformat an upstream file that is not formatter-clean, which moved a lint-disable comment off the line it covered. After the commit, compare `git diff --name-only <tag> HEAD` with Oficina's own files and fix any other file by hand.
- A clean-looking merge can still fail the gates where an upstream change meets Oficina's: a new upstream test built params without a field the workspace split makes required. Fix each in its own commit on the `sync/<tag>` branch with the smallest edit, and list it in the notes file.
- The gates run only Oficina's tests. For a large release also run the unit suite over every directory Oficina touches, for example `git diff --name-only <old tag> oficina -- src | xargs -n1 dirname | sort -u` passed to `node node_modules/vitest/vitest.mjs run --config config/vitest.config.ts`. On the first sync two tests failed for host reasons only: `src/main/codex-cli/command.test.ts` finds the `claude` and `codex` links in `/usr/local/bin`, and `git-admission-storm-measurement.test.ts` times out under load and passes alone.
- Take upstream's version of `.github/workflows/*` whole: Oficina never edits workflows, and Actions are disabled on the fork.

### Cadence and rules

- Weekly, and whenever the Orca phone app updates: the phone refuses a desktop whose protocol is older than it expects, so a lagging Oficina stops pairing.
- `oficina` is never rebased, squashed over an upstream merge, or force-pushed. Upstream history must stay in it, because "last merged" is read from the tags reachable from `oficina`. Only the sync PR itself is merged with a merge commit; feature PRs into `oficina` are squash-merged as usual.
- The PR always targets the fork (`origin`); the script refuses to run when `origin` is `stablyai/orca`.
